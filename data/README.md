# Data

Nothing in here except this file, `splits.json`, `real/corners.json`, `real/annotations/` and
`real/transcripts/` is tracked by git — image blobs stay local. See the root `.gitignore`.

How the buckets are *used* — the splits, the frozen evaluation sets and the generator that consumes
them — is in [`docs/datasets-and-splits.md`](../docs/datasets-and-splits.md).

The single most important rule in this project:

> **`data/real/` is evaluation-only.** Its photos and reference scans must never enter a training
> loop, and the degradation pipeline must never touch them — they arrive degraded by reality.

## Buckets

| Path | What | Count | Provenance | Used for |
|---|---|---|---|---|
| `scans/` | Clean, flat, high-resolution A4 document scans (~2480×3512 RGB) of handwritten computer-vision lecture notes | 50 | Provided by the teaching staff | **Training targets.** Warped onto backgrounds + degraded to synthesise the whole training set |
| `backgrounds/` | Background-only phone photos (1920×2560), named for the surface they show: `carpet-*`, `fabric-*`, `floor-*`, `leather-*`, `plain-*`, `stone-*`, `tile-*`, `wood-*` | 20 | Shot by the author | Surfaces the scans get composited onto. The train / held-out split is recorded in `splits.json`, not by moving files — one copy of each photo, and the split stays re-derivable |
| `real/photos/` | Real smartphone photos of documents the model has never seen in any form (1920×2560, no EXIF rotation) | 19 | Shot by the author | **Evaluation only.** The real-world test set |
| `real/reference/` | Output of a commercial scanning app (CamScanner / Adobe Scan) for each photo in `real/photos/`, same filename | 19 | Captured by the author | **Evaluation only.** A commercial baseline to compare against — *not* ground truth, and never a training target |
| `real/annotations/` | Roboflow keypoint export (COCO Keypoints JSON): four page corners per photo, ordered TL → TR → BR → BL | 1 file | Labelled by the author in Roboflow | Ground-truth corners for the corner-detection test set, and for rectifying photos before enhancement |
| `real/corners.json` | The parsed annotations, one ordered `(4, 2)` array per photo in **original photo pixels** | — | Generated by `scripts/parse_roboflow.py` | What the code actually reads |
| `real/transcripts/` | Hand-typed ground-truth text for the printed documents, `ImageNN.txt` | ~5 | Typed by the author | Character error rate for the OCR readability study |
| `cache/scans_1600/` | `scans/` downscaled to 1600 px on the long side | 50 | Generated by `scripts/prepare_data.py` | Speed only — warping 2480×3512 inside every `__getitem__` is the throughput bottleneck |
| `frozen/<task>/<split>/` | Synthetic evaluation samples generated **once** with a fixed seed: one composited photo per sample plus `manifest.json` with its corners, source scan and every degradation parameter. `task` is `enhance` or `corner`, `split` is `train`, `val` or `test` | 6 × 200 | Generated by `scripts/freeze_eval_sets.py` | So every epoch and every model is scored on *identical* images — otherwise the validation curve measures the dice as much as the model. **One set per task**, because the corner detector's samples carry tinted stock and curled pages that the enhancement network has no clean target for |
| `splits.json` | Which scan ids and which backgrounds belong to train / val / test | — | Generated by `scripts/prepare_data.py` | The split is **by source scan**, so two degraded versions of the same page can never land on opposite sides |

## Why the real photos are diverse on purpose

They are the only preview of what the graders will hand the model on presentation day, so they vary
lighting (daylight, warm lamp, harsh overhead, a shadow falling across the page), viewpoint (angle,
distance, rotation), background (wood, carpet, marble, red table, cluttered desk) and camera behaviour
(shake, imperfect focus). They also deliberately include hard cases the synthetic pipeline does not
model well — a bound notebook, an open two-page spread, a dark printed card — which is where the
failure analysis in the report comes from.

Roughly six of them are **printed** text (English exam sheets, a Persian form and a card); the rest
are handwritten. Only the printed ones give a meaningful character error rate — Tesseract cannot read
handwritten Persian, so the rest are compared by the engine's own word confidence instead.

## Why only the composited photo is stored for a frozen sample

Everything else about a frozen sample is *derived* from it: the rectified input and clean target for
the enhancement network come from the recorded corners and the cached scan, and the corner heatmaps
come from the corners. That is deliberate — the evaluation path and the training path then run the
same code, so they cannot drift apart, and 400 samples cost 72 MB instead of well over a gigabyte.
The photos are stored as quality-96 JPEG, which matters not at all: the last stage of the degradation
pipeline is itself a quality 30–80 re-encode.

Because the samples are a pure function of their key, `sanity_checks.py` re-generates a few of them
and compares the bytes. If the generator changes, that check fails loudly — which is the point.
Numbers measured on an old frozen set are not comparable with numbers from a new one.

## Refilling from scratch

```bash
# 1. drop the provided scans into data/scans/
# 2. drop your photos into data/real/photos/ and app outputs into data/real/reference/
# 3. drop background photos into data/backgrounds/
# 4. export Roboflow as COCO Keypoints into data/real/annotations/
python scripts/prepare_data.py        # caches scans, writes splits.json
python scripts/freeze_eval_sets.py    # writes frozen/<task>/{train,val,test}
python scripts/sanity_checks.py       # verifies all of the above
python scripts/preview_synth.py       # renders samples to outputs/previews to inspect by eye
```

Parsing the Roboflow keypoint export into `real/corners.json` is not built yet — it is waiting on the
export itself.
